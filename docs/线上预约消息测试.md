## 2. 确认本店接收人已绑定

在「管理后台消息推送 → 店长微信提醒」点「刷新绑定状态」，应显示本店接收人已确认绑定。

尚未绑定时，在「用户管理」确认有属于该门店的有效店长账号。选择该账号，生成微信绑定链接，由店长本人用准备接收消息的微信在 15 分钟内打开。先关注正确的服务号，再点击「本人确认绑定并接收通知」，回后台刷新绑定状态。

每店一位接收人，总部账号不能直接替代本店账号。绑定已正常时无需重新生成链接；重新生成会等待新一轮本人确认。新配置用新预约验证，历史未发送记录不会自动补发。

## 3. 客户真机提交一笔测试预约

使用当前小程序的开发版预览或体验版，在真实微信中登录；客户端 API 指向 `https://mp-admin.hetuonian.cn`。可使用两个微信分别扮演客户和店长，便于核对两端收件。

1. 选择刚才绑定的同一家门店、已上架品项、1 人及可用时段。建议选择约一小时后的时段，以便有时间核验店长通知和确认操作。
2. 称呼填「消息测试」，联系电话填写测试者自己的有效号码，备注填「消息联调测试，请勿实际排班」。
3. 点击最终的「提交预约」，允许「预约处理提醒」和「预约提醒」两个一次性订阅模板。若微信已记住同意选择，可能直接返回授权结果而不再次弹窗；以本次返回和服务端记录为准。
4. 保存预约编号。不要在此时从后台立即确认，先等店长待接单通知。

当前产品在提交预约、提交改约的点击动作中申请订阅，已经取消独立的「订阅预约及到店提醒」卡片；无需寻找该按钮。H5、模拟登录和后台直接代建预约不能替代本步骤的真机订阅授权。

## 4. 按顺序验收三条微信消息

| 顺序 | 操作 | 预期 |
| --- | --- | --- |
| A | 提交后等 10～30 秒，必要时刷新消息中心 | 后台出现待确认预约与站内消息；本店店长在服务号收到待接单提醒，含项目、时间、顾客手机号、本店摘要 |
| B | 确认 A 已收到后，后台「预约管理」找到同一预约并确认 | 客户收到「预约处理提醒」，内容对应同一预约；店长不再收到这笔预约的旧待接单提醒 |
| C | 保持预约为已确认，等待到店提醒时间范围 | 客户收到独立的「预约提醒」；每分钟扫描任务，进入范围后再等 1～2 分钟核对 |

当前上海中心店只读返回：最短提前 30 分钟、到店前 15 分钟提醒。例如预约 19:00 并在此前确认，应在约 18:45 后的扫描周期触发到店提醒。实际以测试门店当前预约规则为准，不为缩短测试等待而修改全店生产规则。

后台「消息中心」分别选「客户消息推送」「管理后台消息推送」，渠道选「微信个人消息」，按预约编号核对事件及发送状态。PC 的 AVAILABLE 不能替代微信发送结果。

- `ACCEPTED / 接口已受理`：微信接口受理；还需手机实际收到才通过验收。
- `BLOCKED / 未发送或条件未满足`：读取该条的具体原因，常见为未绑定、客户未授权、模板字段或密钥未配置。
- `UNKNOWN / 发送结果待核实`：先核对手机及完整原因，避免用重复提交掩盖问题。
- `CANCELLED / 已停止发送`：核对是否预约已提前处理或更新、渠道关闭或接收人变更。

一次性授权按模板独立消费。收到一次处理结果后，直接再取消并不保证还有新的处理通知额度；若要测试拒绝、改约或取消，用新一笔测试预约并核对当次授权。客户拒绝订阅仍可预约，未授权时不应当被标记为成功发送。

## 5. 失败时读取本项目记录

优先复制消息中心里对应预约的事件、发送状态和完整原因。需要服务器记录时，在服务器终端执行下面这一条，只读访问本项目独立数据库，不输出客户正文、手机号、OpenID 或密钥：

```bash
sudo docker exec yuwatang-mysql-isolated mysql --defaults-extra-file=/run/secrets/client.cnf --protocol=socket --database=yuwatang_reservation --batch -e "SELECT store_id,appointment_id,channel,event_type,delivery_status,attempts,last_error,created_at FROM notification_outbox ORDER BY created_at DESC LIMIT 20;"
```

`SERVICE` 是店长服务号，`SUBSCRIBE` 是客户订阅，`INBOX` 是后台站内消息。该查询不强制派发、不重置授权次数、不修改状态。健康检查成功不能代替这三条实际发送记录。
