适用部署：`yuhetang-java-api` 容器，`booking.hetuonian.cn` 客服回调，`mp-admin.hetuonian.cn` 管理后台。

## 当前已确认的情况

2026-11-07 已通过独立脚本实际切换到 Java `20261107-215000`；运行镜像、JAR 校验值、Docker 健康及数据库连接均已核对。22:52:31 真实客户文字回调显示 `WeChat callback type=text event=none outcome=STORED`，用户确认管理后台已出现客户文字。接收、入库及后台显示已完成本次验收。

后台对这条会话发送新回复时，客户仍未收到，页面显示 HTTP 412。本地已复现微信发送接口拒绝分块请求，修复及更新步骤见[微信客服 HTTP 412 修复](微信客服HTTP412修复-20261107.md)。实际发送送达尚待修复版本部署后验收。

此前的历史快照：Java 195806 下签名 GET 与加密 POST 的本机和公网四项检查通过，但独立数据库只出现进入会话事件和旧 `OUT / UNKNOWN`，没有客户文字。该快照描述更新前状态，不能用于否定现在的 `text/STORED` 和后台实际显示结果。

微信进入会话事件和客户文字是两种推送；进入事件能够创建会话和短时回复额度，却没有文字内容。小程序客服的收发机制见[接收消息和事件](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/customer-message/receive.html)和[发送客服消息](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/customer-message/send.html)。

## 检查正在运行的容器

上传 `yuhetang-wechat-check-20261107-v2.py` 和同名 `.sha256` 到 `/home/ubuntu`，在服务器终端执行（旧版已通过四项检查时，无须为了再验证一次而重复运行）：

```bash
cd /home/ubuntu
sha256sum --check yuhetang-wechat-check-20261107-v2.py.sha256
sudo python3 yuhetang-wechat-check-20261107-v2.py
```

脚本使用 Ubuntu 的 Python 3、Docker 和 OpenSSL。它从**正在运行的容器**读取微信配置，仅输出 AppID 是否匹配、配置是否存在及 HTTP 检查结果；不会输出 Token、AESKey、AppSecret、完整签名 URL 或客户内容。

四个检查正常时应显示：

```text
Local signed GET: PASS HTTP=200
Local encrypted POST: PASS HTTP=200
Public signed GET: PASS HTTP=200
Public encrypted POST: PASS HTTP=200
```

POST 使用 `yht_diagnostic_probe` 诊断事件。现有接收逻辑在任何数据库写入前忽略该事件；不会创建客户或会话，也不会发出客服消息或请求新的微信 access_token。检查过程中会增加普通 HTTP 访问日志。

- 本机 GET 失败：先核对实际运行容器及其微信配置。
- 本机 POST 失败：检查 AESKey、AppID 及 Java 错误记录。
- 本机通过而公网失败：检查当前域名的 HTTPS、反向代理和访问控制。
- 四项通过：证明当前容器的验签、解密及公网转发可用。仍须验证真实微信文字回调和入库，不能以诊断通过替代客服验收。

新版脚本直接读取当前 OpenResty 容器内的日志，以本次公网 POST 的随机标识核对，并最多等待 6 秒。只有 `Current public POST found in this log: True` 才确认这份文件实际记录了本次请求。如果为 False，先检查正在加载的配置：

```bash
sudo docker exec 1Panel-openresty-Iiuu nginx -T 2>&1 |
  awk '/^# configuration file / {print} /^[ \t]*(server_name|access_log|error_log)[ \t]/ {print}'
```

确认 `booking.hetuonian.cn` 对应的实际 `access_log`，以及该路径在容器与宿主机之间的挂载。日志关闭、缓冲尚未刷新、路径不同或格式不含完整请求参数，都会使当前文件无法用于判断请求是否到达。

## 捕获下一条真实客户消息

确认日志位置后保持下面命令运行；若实际路径不同，先替换路径。再用未绑定为客服的另一个微信号从小程序进入客服，发送一条新的文字。用两个账号测试可以明确区分客户和接待人员身份；不据此认定同账号就是故障原因。

```bash
sudo tail -n 0 -F /opt/1panel/www/sites/wechat-callback/log/access.log |
  awk '/POST \/api\/wechat\/customer-service/ {sub(/\?.*/, "", $7); print $4, $5, $6, $7, $9; fflush()}'
```

诊断脚本自己的 POST 也会出现，必须与随后手机实际发文字的时间分开。按 Ctrl+C 结束监听。

- 已确认实时记录请求的日志中，手机发文字时没有新 POST：继续检查微信侧实际投递及该测试会话的账号来源。未验证日志本身的实时性时不能作此推断。
- 新 POST 返回非 200：结合该时间的 Java/代理日志定位验签、解密、权限或处理错误。
- 新 POST 返回 200、后台仍无文字：继续核对已验证消息类型、存储结果、会话归属和后台列表接口。
- 后台出现新文字后才进行一次新回复，以新消息的发送结果和客户实际收到为准；历史失败记录不会因更新自动变为成功。

## Java 新版的诊断日志

本次 Java 更新不改数据库结构或历史消息，只补充收发结果的诊断。接收端在验签、解密和事务完成后记录 `type`、`event`、`outcome`；异常记录 HTTP 状态或异常类别，不记录正文、OpenID、签名参数或密钥。发送端仍不自动重发：不确定结果保持 `UNKNOWN`，后台会显示具体连接、TLS、HTTP 或解析原因。

```bash
sudo docker logs --since 10m --tail 200 yuhetang-java-api 2>&1 |
  grep -E 'WeChat callback|WeChat customer send'
```

典型记录：

```text
WeChat callback type=event event=user_enter_tempsession outcome=ENTRY
WeChat callback type=text event=none outcome=STORED
WeChat callback type=text event=none outcome=DUPLICATE
WeChat customer send message=<本系统消息编号> state=UNKNOWN category=READ_TIMEOUT
```

`ENTRY` 表示进入窗口，`STORED` 表示客户文字/图片/卡片已入库，`DUPLICATE` 表示微信重试的同一条消息已处理；`IGNORED` 表示不属于支持的客服类型。`REJECTED` 或 `ERROR` 表示该请求未正常处理。只有 `ENTRY` 没有 `text/STORED` 时，仍需解决微信文字投递路径；不应制造模拟客户消息或把旧失败记录修改为成功。
