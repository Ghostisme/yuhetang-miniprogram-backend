# 微信客服回调检查

适用部署：`yuhetang-java-api` 容器，`booking.hetuonian.cn` 客服回调，`mp-admin.hetuonian.cn` 管理后台。

## 当前已确认的情况

2026-11-07 的服务器输出确认 Java 镜像 `20261107-195806` 正在运行。回调访问日志包含 18:44:57、19:17:43、20:50:18 三条返回 200 的 POST，但本次新发的客户文字没有对应记录。公网访问新后台的健康接口成功；公开门店接口返回 0 家启用门店。上述证据尚不能证明客户文字的接收和回复链路已通过。

微信进入会话事件和客户文字是两种推送；进入事件能够创建会话和短时回复额度，却没有文字内容。小程序客服的收发机制见[接收消息和事件](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/customer-message/receive.html)和[发送客服消息](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/customer-message/send.html)。

## 检查正在运行的容器

上传 `yuhetang-wechat-check-20261107.py` 和同名 `.sha256` 到 `/home/ubuntu`，在服务器终端执行：

```bash
cd /home/ubuntu
sha256sum --check yuhetang-wechat-check-20261107.py.sha256
sudo python3 yuhetang-wechat-check-20261107.py
```

脚本使用 Ubuntu 的 Python 3、Docker 和 OpenSSL。它从**正在运行的容器**读取微信配置，仅输出 AppID 是否匹配、配置是否存在及 HTTP 检查结果；不会输出 Token、AESKey、AppSecret、完整签名 URL 或客户内容。

四个检查正常时应显示：

```text
Local signed GET: PASS HTTP=200
Local encrypted POST: PASS HTTP=200
Public signed GET: PASS HTTP=200
Public encrypted POST: PASS HTTP=200
```

POST 使用 `yht_diagnostic_probe` 诊断事件。现有接收逻辑在任何数据库写入前忽略该事件；不会创建客户或会话，也不会发出客服消息或请求新的微信 access_token。检查过程中会增加普通 HTTP 访问日志。

- 本机 GET 失败：先核对实际运行容器及其微信配置。
- 本机 POST 失败：检查 AESKey、AppID 及 Java 错误记录。
- 本机通过而公网失败：检查当前域名的 HTTPS、反向代理和访问控制。
- 四项通过：证明当前容器的验签、解密及公网转发可用。仍须验证真实微信文字回调和入库，不能以诊断通过替代客服验收。

## 捕获下一条真实客户消息

保持下面命令运行，再用未绑定为客服的另一个微信号从小程序进入客服，发送一条新的文字。用两个账号测试可以明确区分客户和接待人员身份；不据此认定同账号就是故障原因。

```bash
sudo tail -n 0 -F /opt/1panel/www/sites/wechat-callback/log/access.log |
  awk '/POST \/api\/wechat\/customer-service/ {sub(/\?.*/, "", $7); print $4, $5, $6, $7, $9; fflush()}'
```

诊断脚本自己的 POST 也会出现，必须与随后手机实际发文字的时间分开。按 Ctrl+C 结束监听。

- 手机发文字时没有新 POST：继续检查微信侧实际投递及该测试会话的账号来源；此时没有证据支持修改聊天列表或数据库来解决。
- 新 POST 返回非 200：结合该时间的 Java/代理日志定位验签、解密、权限或处理错误。
- 新 POST 返回 200、后台仍无文字：继续核对已验证消息类型、存储结果、会话归属和后台列表接口。
- 后台出现新文字后才进行一次新回复，以新消息的发送结果和客户实际收到为准；历史失败记录不会因更新自动变为成功。
