## 后台使用

进入「客户档案」，找到已核实的会员，点击「会员余额」。

- 总部：录入期初账户、查看各店余额、登记充值/消费、对充值/消费做反向冲正。
- 店长：查看并登记自己门店的充值/消费。
- 前台：默认只读自己门店的余额与流水。
- 自定义角色需配置「会员余额」下的相应权限；期初与冲正仅限总部。

期初账户必须填写所属门店、原系统账户唯一编号、账户名称、实际余额、核对截止时间、原始凭证编号和核对说明。相同「门店＋原账户编号」不允许再次建账或覆盖；同一客户有多个门店账户时分别保存。未录入账户表示待迁移核对，不能解释为余额为零。

## 分批迁移期间的查询判定

会员仍在酷鼠、陆续迁入新后台期间，余额只从本系统已核对入账的账户读取。手机号已授权、客户档案已建立，并不代表会员身份或余额已迁移；不会自动拿累计充值、测试金额或缺失值作为余额。

| 新后台当前状态 | 查询状态 | 小程序及服务号提示 | 金额含义 |
| --- | --- | --- | --- |
| 未确认会员，且没有余额账户 | `MEMBERSHIP_PENDING` | 会员资料待核实；暂未查到不代表非会员或余额为零 | `totalFen=null`，不展示虚构的 0 |
| 已确认会员，没有余额账户 | `MIGRATION_PENDING` | 余额待迁移核对，请门店核对原账户 | `totalFen=null` |
| 存在已迁入的账户 | `AVAILABLE` | 展示各账户余额、流水，并注明只包含已迁入账户 | `totalFen` 仅为已迁入且在查询权限范围内的账户合计；真实零余额仍为 `0` |

客户可先完成手机号授权及服务号绑定。后续迁入时，按同一已授权手机号找到现有客户档案，在该档案确认会员身份并录入期初账户；客户刷新小程序或再次发送“余额”即可查询，无需重新绑定。不得为同一客户另建无关联档案，否则无法依靠原绑定查询。

总部在「客户档案 → 会员余额」能看到以上状态。会员身份尚未核实时，期初录入按钮不可操作；先在客户档案确认会员标识，再核对该账户的来源、门店与金额。分店只查询和维护权限范围内的账户，看不到其他店的账户不代表该客户在其他店没有余额。

同一客户可分批迁入不同账户。已有一个门店账户不表示所有门店迁移完成，页面和服务号均会说明展示范围。查询错误与账户待迁移分别提示，接口失败时不会把旧金额或 `0` 当成最新结果。

金额以人民币元输入、数据库以整数分保存。每次金额变动均写入独立流水，并检查账户版本与重复提交标识。原流水不修改、不删除。冲正保留原流水，只允许一次反向登记；不允许把余额扣成负数。界面显示提交不确定时，先刷新核对流水；原弹窗重试沿用同一提交标识。

这些操作登记已核实的线下交易。本次未接入微信收款，也未开启预约自动扣款或跨店自动结算；现有跨店支付预留继续独立保留。

## 客户在小程序查看

微信登录后，在「我的预约 → 个人资料」或个人资料页点击「会员余额与流水」。客户先单独授权手机号，系统按本人已验证手机号关联客户档案，只返回本人账户。每个账户展示门店、名称、当前余额和变动流水，流水每页 20 条。已有姓名但未授权手机号时会提示先核实身份。

余额页已接入中文、英文、日文界面。业务账户名称和客户原始资料不做自动翻译或修改。

## 服务号配置

服务号使用 AppID `wxf9ad4dfd7684097a`。新的会员查询回调为：

```text
https://mp-admin.hetuonian.cn/api/wechat/service/messages
```

这与小程序客服回调 `/api/wechat/customer-service`、店长绑定授权回调 `/api/wechat/service/callback` 分别处理。不要将这三个地址互相替换。

先部署新的 Java，保留现有服务号 AppID 与 AppSecret 配置，在服务器 `/etc/yuwatang-reservation.docker.env` 配置下面三项。密钥留在服务器和微信管理后台，不发送到聊天、前端或 Git 仓库。

```dotenv
SERVICE_MESSAGE_TOKEN=在服务器生成的3至32位英文字母数字令牌
SERVICE_MESSAGE_AES_KEY=微信后台随机生成的43位EncodingAESKey
SERVICE_MESSAGE_ALLOW_PLAINTEXT=false
```

Token 可在服务器使用 `openssl rand -hex 16` 生成；将结果分别填入 env 与微信后台 Token 字段。AESKey 在微信后台点击「随机生成」，将同一个值填入上述 env。保留 env 文件 root 所有、0600 权限。

环境变量在创建 Docker 容器时读取。仅执行 `docker restart` 不会加载 env 文件的新内容；须按 Java 更新流程保留旧容器后，用新版 `run.sh` 重新创建容器。请先按 `deploy/docker-java/README.md` 备份、校验并切换，确认 `/api/health` 正常，再切换微信回调。

在服务号后台「消息推送」填写新 URL、相同 Token 和 EncodingAESKey，选择「安全模式」和「XML」，提交验证后启用。继续沿用现有 HTTPS 站点的 `/api/` 反向代理即可，无需安装另一个 OpenResty。

当前服务号的旧酷鼠 URL 是接收微信事件的地址，不是读取余额的接口。切换后，酷鼠将不再收到这条服务号回调；旧系统依赖回调的自动回复需要一起确认。现有自定义菜单及店长模板消息发送接口保持独立，菜单已有的旧酷鼠查询链接也不会被本次代码自动改写。

## 首次绑定及日常查询

1. 客户在小程序完成微信登录与手机号授权，进入「会员余额与流水 → 服务号查询」。
2. 点击「生成绑定口令」，复制完整的 `绑定 XXXXXXXXXXXX`，5 分钟内发到裕和堂服务号。绑定口令仅用于本人会员档案，不能转发给他人。
3. 服务号回复绑定成功及当前账户余额；以后发送「余额」「查余额」「会员余额」或 `balance` 即可查询。服务号最多展示前 6 个账户，其余在小程序查看。
4. 发送「解绑」或在小程序解除绑定，会停止服务号余额查询；重新查询需重新绑定。手机号档案变化后，原绑定失效，需重新核实。

小程序 OpenID、服务号 OpenID 和店长接收人绑定分别保存，不直接混用。回复通过当前入站消息被动返回，不使用客户预约订阅模板或店长模板；无需为余额查询另选消息模板。

## 正式余额迁移

前面的 200 条会员表格是验证样本，字段 `money` 在来源中存在「余额或金额」的语义不确定性，累计充值也不是可用余额。本次不把这些值自动写成客户资产。

支持按客户、门店或账户逐批迁移。每一批先由客户确认原账户在酷鼠停止记账的截止时间，导出该批账户的实际剩余金额。按门店、原会员/卡账户编号匹配，先核对单店总额和客户重名/同手机号的多账户，再由总部录入已确认期初。该账户迁入后的充值与消费在新后台维护，尚未迁入的账户继续由原系统核对，避免同一笔交易在两边重复登记。累计充值、历史消费和本金/赠送金的抵扣规则，不能在缺少确认时混成新的余额。

代码只在 `yuwatang_reservation` 中新增 V14 余额/流水/绑定相关表与权限。不连接其他业务库，不修改既有客户、预约、品项或会员来源数据，不自动运行样本资金导入。

## 联调验收

使用明确标识的测试会员和测试金额，核对：

1. 总部建账后，小程序本人查询与后台余额一致，其他客户不能读取；会员资料待核实与余额待迁移分别提示，不用 `0` 替代未知。已核对的零余额能正常查询。
2. 同一客户两店账户独立；店长不能查询或登记其他门店的流水，前台不能改余额。
3. 充值、消费、冲正各做一次，前后金额及流水匹配；余额不足被拒绝；重复提交不重复记账。
4. 服务号绑定前不返回余额，绑定后「余额」回复与小程序一致；解绑或更换已验证手机号后旧绑定不能继续读取。
5. 安全模式校验、加密收发以及微信重试不重复处理；小程序客服与店长预约提醒分别再测试一次。
6. 客户先绑定服务号，再按同一档案分两批迁入不同门店账户；每批迁入后直接再次查询，无需重新绑定，也不把已迁入的小计当成完整会员资产。

本地自动化使用隔离的 H2 数据库及合成消息验证。真实服务号入站、手机显示、生产 MySQL 迁移与旧系统最终数据核对，需在部署后完成，不能用本地通过替代。
