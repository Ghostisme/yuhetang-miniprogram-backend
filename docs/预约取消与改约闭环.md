# 预约取消、改约及店长详情验收

本轮新增 V11 `appointment_reschedule`，仅在本项目数据库新增改约申请表。原预约、历史、会员、客服及门店独立品项继续保留；不重新初始化数据。

## 客户可操作时间

客户仅可在待确认或已确认预约的自助截止时间之前取消、申请改约。截止时间为到店开始时间减去本店预约规则 `cancelHours`（默认 2 小时）。等于截止时间时已经关闭；规则为 0 时也不能在预约开始及之后操作。到店、完成、取消、未到店状态均不再允许客户取消或改约。

Java 对修改接口及改约时段查询统一校验，页面根据服务端返回的 `customerActions` 显示操作。手机显示期间每秒更新截止状态；使用服务端时间加收到响应后的经过时间，避免手机时钟错误。旧服务端未返回操作策略时隐藏自助按钮并提示刷新。

## 改约闭环

1. 客户选择不同的日期或时间后提交申请，保留原预约状态、时间、人数、已分配人员及名额；新时段不提前占位。不能同时提交第二条待处理申请。
2. 管理后台增加「改约待处理」筛选。店长消息及站内消息可直接打开对应预约。详情并列展示原预约和申请时间、人数、处理期限及说明。
3. 门店点击「确认改约并通知客户」，在同一事务和门店锁内重新检查名额。成功后新时间生效，预约变为已确认，重新安排实际调理师；原时段名额释放。名额不足时操作失败，原预约与申请保留供协调。
4. 门店未通过必须填写原因，原预约继续保留。客户可撤回尚未处理的申请，撤回也保留原预约。
5. 处理期限取原预约开始时间与新时间减最短提前分钟数两者较早者。到期后申请立即在查询中显示失效，后台每分钟关闭到期申请并记录历史；不会自动取消原预约。
6. 取消、拒绝原预约、到店、完成或未到店操作会关闭尚未处理的改约申请。版本冲突必须刷新，不自动重复提交。

客户改约申请会产生店长待办；确认、未通过或失效使用客户的预约处理提醒模板，并按该模板可用的一次性授权次数发送。客户撤回不消耗一条处理提醒授权。未授权、配置不全或微信拒绝时，消息中心保留原因，不能把未发送当作已送达。

## 真机验收

先更新本轮 Java 和管理后台，再用本轮编译结果上传新的小程序体验版，并在手机重新进入该版。仅更新服务器不会替换微信已经下载的旧页面。

1. 「我的预约」不应出现独立订阅卡片、次数或「订阅预约及到店提醒」按钮。订阅请求只在提交预约、提交改约的用户点击中发起；微信记住选择时不保证每次重新弹窗。拒绝授权仍可提交业务。
2. 用新的测试预约检查服务号消息中的五字段，点击「查看详情」：未登录先登录、登录后自动打开同一编号，不需要手动搜索。核对门店、项目、客户、电话、时间及当前状态。
3. 另用超过本店自助提前小时数的未来预约测试改约。申请后客户仍看到原时间；店长收到申请新时间的待办。门店确认后两端变为新时间并检查客户微信实际收件。
4. 再测试未通过、客户撤回、处理超时和新时段被占满，均核对原预约是否保留及历史记录。已确认并不代表客户永远可取消；截止时刻后接口应拒绝取消和申请改约。
5. 用其他门店账号打开同一消息链接，应提示无权访问而非泄露预约。所有测试结束后由门店后台清理测试预约释放名额。

本地验证使用 H2 隔离测试库、模拟微信接口和拦截 API 的浏览器。Docker 在目标服务器启动、迁移与真实微信收件需要部署后单独验收。
