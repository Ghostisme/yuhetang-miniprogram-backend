# 部署和微信接入

## 运行方式

本地运行以本仓库 README 为准，客户页、管理后台和 API 使用同一个 8790 端口。`tools/start-local.ps1 -Build` 构建前端并打进 Spring Boot JAR。`data/` 保存本仓库独立数据库、JWT 本地密钥及上传图片，`logs/` 保存启动日志，均不应提交仓库。

正式部署采用 Java 17，先在相邻 `yuhetang-miniprogram-admin/` 运行 `npm ci`、`npm run build`，再在本仓库根目录执行 `mvn -Prelease package`。仓库不相邻时通过 `-Dfrontend.dist=前端dist绝对路径` 指定。将 `target/reservation-1.0.0.jar` 部署到独立应用目录，通过环境变量配置后运行 `java -jar reservation-1.0.0.jar`。正式服务由进程管理器负责启动和重启，反向代理提供 HTTPS。

| 配置 | 正式环境要求 |
| --- | --- |
| `APP_MODE` | `production`；关闭本地模拟客户登录，不创建门店演示账号或示例调理师 |
| `JWT_SECRET` | 至少 32 位随机密钥，安全保存，轮换后原登录失效 |
| `ADMIN_PASSWORD` | 独立初始总部管理员密码；初次建库时生效 |
| `PORT` / `BIND_ADDRESS` | 默认 8790 / 127.0.0.1，通常由同机反向代理访问 |
| `APP_DATA_DIR` | 本应用独立的绝对路径，供上传图片及数据文件使用 |
| `DB_URL` / `DB_USERNAME` / `DB_PASSWORD` | 独立数据库及最小权限账号；留空默认使用本地 H2 |
| `PUBLIC_URL` | 正式 HTTPS 域名，例如 `https://booking.example.cn` |
| 微信配置 | 见以下各接入步骤，密钥只放在后端环境变量 |

MySQL 示例连接：`jdbc:mysql://127.0.0.1:3306/yuwatang_reservation?useUnicode=true&characterEncoding=UTF-8&serverTimezone=Asia/Shanghai`。请预先创建专属空库，Flyway 首次启动建表。本次验证使用项目独立 H2；未连接现有其他业务数据库，也未执行 MySQL 部署验证。禁止直接把演示 H2 或模拟账号作为正式客户数据库。

保留数据库和 `APP_DATA_DIR/uploads/` 的备份；H2 文件备份应先停服务或使用数据库一致性备份方式。应用可重新构建，客户资料及上传文件需要单独备份。业务时间按上海时区处理。

## 小程序登录和微信客服

1. 客户在微信小程序后台授予开发权限，提供真实 AppID。后端配置 `WECHAT_APP_ID`、`WECHAT_APP_SECRET`。
2. 微信开发者工具导入独立 `yuhetang-miniprogram/` 仓库根目录；修改 `project.config.json` 的 AppID，修改 `config.js` 的 `apiBase` 为正式 HTTPS 域名，保持 `developmentLogin:false`。
3. 微信后台配置 request、uploadFile、downloadFile 合法域名，完善主体、服务类目和隐私保护指引；根据实际权限申请结果验收。
4. 后台添加客服人员。原生小程序门店页、预约页、我的预约等入口已使用 `button open-type="contact"`，由微信官方客服接待界面承接。
5. 真机验证：微信登录 → 留资授权 → 待确认 → 门店处理 → 我的预约 → 客服会话。微信客服由小程序客服账号接待；管理后台提供预约和客户数据管理，不包含自建聊天坐席系统。

H5 用于向客户演示视觉和相同预约流程；浏览器不能直接替代原生小程序客服会话。正式模式的 H5 不提供模拟身份提交入口。

## 客户订阅消息

1. 在客户小程序选择实际可用的预约类订阅模板，设置 `CUSTOMER_TEMPLATE_ID`。
2. 总部后台“扩展与配置”填写客户模板字段映射。模板字段名必须来自客户账号实际模板，映射值只允许 `storeName`、`serviceName`、`time`、`status`、`appointmentId`、`event`。
3. 格式示例：`{"thing1":"storeName","thing2":"serviceName","time3":"time","phrase4":"status"}`。这是结构示例，不能直接假定客户模板的字段也是这些名字。
4. 客户在原生小程序主动点击消息订阅按钮后，授权通过才登记可用次数。预约提交本身不消耗一次确认通知；确认、改约、取消、到店前提醒等事件按可用授权发送。
5. 拒绝订阅不阻止预约。一次授权不等于无限推送；配额不足时如实记录，客户仍可在“我的预约”查看结果。

## 门店管理员个人微信通知

已实现认证服务号模板消息接口和门店接收人绑定流程，没有企业微信群通知依赖。

1. 客户提供认证服务号后台权限，核对模板消息接口能力、适合的新预约/待处理通知模板和字段限制。
2. 后端配置 `SERVICE_APP_ID`、`SERVICE_APP_SECRET`、`SERVICE_TEMPLATE_ID`、`PUBLIC_URL`；服务号后台配置网页授权域名和服务器出口 IP 白名单。
3. 在“扩展与配置”填写服务号模板字段映射，格式与上文相同，字段以服务号实际模板为准。
4. 门店创建有效账号，在“消息与提醒”选择本门店接收账号并生成 15 分钟有效的授权链接。接收人先关注服务号，用本人微信打开链接，完成授权后再点击本人确认绑定。
5. 每个门店保存一个接收人。更换或解绑后，尚未发送给原接收人的队列会停止投递。停用账号同样停止投递。
6. 通过真实新预约验证服务号消息，检查后台发送结果。`ACCEPTED` 仅指微信接口受理，不代表用户已读。

电脑通知使用浏览器 Notification API，需要用户主动授权；页面在后台运行时轮询检查新消息。正式域名应启用 HTTPS。关闭浏览器后依靠服务号通知；没有实现独立 Windows 常驻客户端或 Web Push 服务。

## 消息结果和待确认提醒

后台会保存通知渠道、预约编号、事件、尝试次数和失败原因。缺少账号、模板、绑定或客户订阅时记录 `BLOCKED`，不会显示为已发送。网络错误最多自动尝试三次；业务配置补齐后用新业务事件验收，不自动补发历史已阻断事件。

营业时间内待确认累计达到 15 分钟，提醒门店处理；不自动取消客户申请。已确认预约在到店前提醒窗口触发客户订阅消息。实际是否送达仍受账号权限、模板内容及客户授权影响。

## 客户准备资料

| 类别 | 需要准备 |
| --- | --- |
| 微信账号 | 小程序开发权限、AppID、服务号权限、模板能力及真实客服人员 |
| 门店 | 各店名称、完整地址、电话、地图坐标、营业时间、图片、停约日期、预约规则及接收人 |
| 调理师 | 姓名、门店、照片、等级、擅长、可服务品项、是否展示、休息标识 |
| 品项与品牌 | 品项名称、介绍、时长、照片、门店适用范围；品牌、空间、产品图文及隐私说明 |
| 会员基础资料 | 姓名/称呼、手机号、归属门店、核实会员标识、等级及外部编号；使用后台模板导入 |
| 部署 | 正式服务器、域名、HTTPS、专属数据库、备份位置、账号交接人 |

资料导入支持预检后提交；品项导入保存为内容草稿，需总部检查并发布。会员导入不包含余额、积分、疗程消耗和历史收银记录。

## 验证边界

当前本地 API、浏览器真实业务链路和 Java 集成测试已经运行。正式微信账号登录、客服会话、模板推送、原生开发者工具编译/真机测试、客户服务器部署与提审发布，需要客户真实账号和正式环境后继续完成。不能用 H5 截图代替这些验收。
