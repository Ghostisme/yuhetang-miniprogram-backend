## 运行方式

本地运行以 README 为准，客户页、管理后台和 API 使用同一个 8790 端口。`tools/start-local.ps1 -Build` 构建前端并打进 Spring Boot JAR。`data/` 保存数据库、JWT 本地密钥及上传图片，`logs/` 保存启动日志，均不应提交仓库。

本次正式前端执行 `npm ci`、`npm run build`，将 `dist/` 内容单独部署到 1Panel 的静态网站。Java 在 `backend/` 执行 `mvn -B -ntp -Papi-release verify`，生成不包含后台 HTML/JS/CSS 的 `target-api/reservation-api-1.0.0.jar`。API 发布包提供私有 Java 17 和独立 systemd 服务，具体安装、数据库初始化、反向代理、证书和更新步骤按 1Panel 操作说明执行。服务器无需安装 Node.js 或 Maven。

| 配置 | 正式环境要求 |
| --- | --- |
| `SPRING_PROFILES_ACTIVE` | `production`，加载正式数据库和独立监控端口配置 |
| `APP_MODE` | `production`；关闭本地模拟客户登录，不创建门店演示账号或示例调理师 |
| `JWT_SECRET` | 至少 32 位随机密钥，安全保存，轮换后原登录失效 |
| `ADMIN_PASSWORD` | 独立初始总部管理员密码；初次建库时生效 |
| `PORT` / `BIND_ADDRESS` | 默认 8790 / 127.0.0.1，通常由同机反向代理访问 |
| `APP_DATA_DIR` | 本应用独立的绝对路径，供上传图片及数据文件使用 |
| `DB_URL` / `DB_USERNAME` / `DB_PASSWORD` | 正式环境必须填写独立 MySQL 数据库及本库权限账号；H2 仅用于本地模式 |
| `PUBLIC_URL` | 正式 HTTPS 域名，例如 `https://booking.example.cn` |
| 微信配置 | 见以下各接入步骤，密钥只放在后端环境变量 |

本次 1Panel 包沿用 `deploy/tencent-isolated/env.example` 中固定的 `jdbc:mariadb://127.0.0.1:3307/yuwatang_reservation?...`。新建官方 MySQL 8.4 Docker 容器，驱动名称不代表安装 MariaDB；使用专用目录、库和账号。脚本生成新库密码，容器初始化空库，Flyway 首次启动建表；不导入本地 H2 或门店演示账号。数据库由项目脚本管理，不在面板应用商店重复创建本项目 MySQL。

保留数据库和 `APP_DATA_DIR/uploads/` 的备份；H2 文件备份应先停服务或使用数据库一致性备份方式。应用可重新构建，客户资料及上传文件需要单独备份。业务时间按上海时区处理。

## 小程序登录和微信客服

1. 客户在微信小程序后台授予开发权限，提供真实 AppID。后端配置 `WECHAT_APP_ID`、`WECHAT_APP_SECRET`。
2. 微信开发者工具导入 `miniprogram/`；当前 AppID 已填入 `wxce054e18303efb8a`。包括开发者工具在内默认连接 `https://booking.yuhetangtcm.com`，保持 `developmentLogin:false`；本地联调才显式启用 `useLocalBackend`。日常配置通过 API 更新，详见 [小程序接口更新约定](小程序接口更新约定.md)。
3. 微信后台配置 request、uploadFile、downloadFile 合法域名，完善主体、服务类目和隐私保护指引；根据实际权限申请结果验收。
4. 后台添加客服人员。小程序门店、预约及我的预约入口进入咨询页，可使用在线文字咨询或「使用微信原生客服」按钮。消息推送使用 HTTPS `/api/wechat/customer-service`，配置 Token、EncodingAESKey 安全模式，后端设置对应 `WECHAT_MESSAGE_TOKEN`、`WECHAT_MESSAGE_AES_KEY`。
5. 真机验证：微信登录 → 留资授权 → 待确认 → 门店处理 → 我的预约 → 客服会话。管理后台「客户沟通」按门店接收在线咨询和微信原生回调，并在微信允许的时限及条数内回复。外部客服工具的发出记录不自动同步，详见 [客服与门店品项接入](客服与门店品项接入.md)。

H5 用于向客户演示视觉和相同预约流程；浏览器不能直接替代原生小程序客服会话。正式模式的 H5 不提供模拟身份提交入口。

## 客户订阅消息

1. 已接入实际两组模板：`CUSTOMER_TEMPLATE_ID` 为预约处理提醒，`CUSTOMER_REMINDER_TEMPLATE_ID` 为到店前预约提醒。完整 ID 和字段见实际账号清单。
2. 总部后台“扩展与配置”分别维护两组客户字段映射。映射值只允许 `customerName`、`storeName`、`serviceName`、`time`、`status`、`appointmentId`、`event`。部署环境变量只初始化缺失的映射，不覆盖总部已保存的配置。
3. 处理提醒使用 `name1/date2/thing3/thing4/phrase5`，到店提醒使用 `thing31/time2/thing7/thing8/phrase11`。预约时间保留日期和时刻。
4. 客户在原生小程序主动点击消息订阅按钮后，按实际接受的模板分别登记次数。确认、拒绝、改约、取消使用处理模板，到店前提醒使用提醒模板；重试复用已预留的授权，不重复扣次数。
5. 拒绝订阅不阻止预约。一次授权不等于无限推送；配额不足时如实记录，客户仍可在“我的预约”查看结果。

## 门店管理员个人微信通知

已实现认证服务号模板消息接口和门店接收人绑定流程，没有企业微信群通知依赖。

1. 客户提供认证服务号后台权限，核对模板消息接口能力、适合的新预约/待处理通知模板和字段限制。
2. 后端配置 `SERVICE_APP_ID`、`SERVICE_APP_SECRET`、`SERVICE_TEMPLATE_ID`、`PUBLIC_URL`；服务号后台配置网页授权域名和服务器出口 IP 白名单。
3. 在“扩展与配置”填写服务号模板字段映射，格式与上文相同，字段以服务号实际模板为准。
4. 门店创建有效账号，在“消息中心”选择本门店接收账号并生成 15 分钟有效的授权链接。接收人先关注服务号，用本人微信打开链接，完成授权后再点击本人确认绑定。
5. 每个门店保存一个接收人。更换或解绑后，尚未发送给原接收人的队列会停止投递。停用账号同样停止投递。
6. 通过真实新预约验证服务号消息，检查后台发送结果。`ACCEPTED` 仅指微信接口受理，不代表用户已读。

电脑通知使用浏览器 Notification API，需要用户主动授权；页面在后台运行时轮询检查新消息。正式域名应启用 HTTPS。关闭浏览器后依靠服务号通知；没有实现独立 Windows 常驻客户端或 Web Push 服务。

## 消息结果和待确认提醒

后台会保存通知渠道、预约编号、事件、尝试次数和失败原因。缺少账号、模板、绑定或客户订阅时记录 `BLOCKED`，不会显示为已发送。微信网络错误最多自动尝试三次；短信仅对明确限流等拒绝最多尝试三次，超时等结果不明确时暂停自动重发；业务配置补齐后用新业务事件验收，不自动补发历史已阻断事件。

营业时间内待确认累计达到 15 分钟，提醒门店处理；不自动取消客户申请。已确认预约在到店前提醒窗口触发客户订阅消息。实际是否送达仍受账号权限、模板内容及客户授权影响。
