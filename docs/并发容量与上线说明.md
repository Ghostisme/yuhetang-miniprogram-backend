# 并发容量与上线说明

当前容量目标按 2026-11-05 的最新确认调整为 **可服务 5 万人的访问规模，先做容量和扩容预留**。访问的统计周期、日活比例和集中高峰尚未确定，首期按实际峰值配置和验收。代码已补齐并发正确性、减少轮询与数据库消耗、过载保护和生产部署入口；目前完成的是开发机隔离验证，尚未完成目标云环境的容量验收。本地仍使用原有 H2 业务库，压测使用另外启动的 MySQL 和合成数据，两者完全隔离。

## 已落地的修改

- 预约创建、改期、规则调整和导入使用数据库事务及固定数量的数据库锁，同一门店的名额校验与写入保持一致；跨门店同手机号限制、重复提交幂等和版本冲突检查同时保留。锁由数据库协调，支持多个后端实例。
- 时段查询按日期汇总占用量，预约列表批量读取门店、养护师和历史，仪表盘按范围聚合统计，减少逐行查询。品牌与门店配置缓存 3 秒，保存成功后本实例缓存失效，其他实例最多延迟 3 秒刷新；可预约名额不使用静态缓存。
- 前端合并相同 GET 请求，给请求设置超时，429/503 按服务端提示冷却；后台列表约 30 秒刷新、未读消息约 15 秒、当前客服对话约 5–6 秒。页面隐藏或小程序页面退出后暂停对应轮询，恢复时加入随机延迟，失败逐步退避。没有自动重放预约等写操作。
- API 对总请求、写操作、密码登录、小程序会话及大文件导入分别设置有限并行数，超限返回 503 和 Retry-After；IP/用户限流返回 429。连接池、线程数、等待时间及 SQL 超时均有上限。限流为每实例控制，尚未实现 Redis 分布式全局配额。
- 通知采用有界线程池，发送前在数据库中抢占任务，外部微信/短信调用期间不占用业务事务；预约提醒用数据库租约协调。超时失联的发送标记 UNKNOWN，需核查渠道结果后处理，避免盲目重发；不能承诺第三方渠道端到端恰好发送一次。
- 提供生产 MySQL 配置、私网监控端口、优雅退出、健康检查、单实例/双实例 Compose、Nginx 压缩与静态缓存、来源 IP 信任配置和独立业务库备份脚本。正式环境不支持用本地 H2 文件做多实例共享数据库。

原有“品牌与内容”的四个页签、门店品项编辑、RBAC、两种客服入口、三类消息通知及大众点评客户/订单导入入口保持原结构。本轮未新增业务模块。

## 实际验证结果

验证日期：2026-11-05。主机有 32 个逻辑 CPU、64 GiB 内存，应用、MySQL 和压测客户端在同一台 Windows 开发机运行，没有限制为 4 核。MySQL 实测版本为 8.0.46；部署模板使用 MySQL 8.4，其容器运行尚未验证。

完整后端回归 **85 项通过**；其中 6 项预约并发测试另外在独立 MySQL 上全部通过。前端 TypeScript 检查与构建、小程序静态检查通过；Compose 完成离线配置校验。生产配置已通过隔离 MySQL 启动检查，生产模式关闭开发登录，Prometheus 通过独立监控端口提供，见 [生产配置检查](capacity-production-smoke-result.json)。微信开发者工具真机编译、真实云端、Docker 镜像构建及容器运行尚未验收。

合成数据：5 万客户身份及客户档案、10 万笔历史已完成预约、300 个管理员。使用有效合成令牌轮换访问；**这并不等于同时建立了 5 万个客户端连接**。请求比例为首页配置 35%、时段查询 30%、我的预约 20%、后台预约列表 10%、仪表盘 5%，均为读取，每档持续 30 秒。

| ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 99.57 | 3,000 | 96.75 ms | 100% | 0 |

累计 **55,500 次 HTTP 200、0 次网络错误、0 次客户端丢弃、0 次服务端拒绝**。第一档包含较明显的预热影响。结果见 [混合读取原始报告](capacity-load-baseline.json)。这组结果不含真实公网、Nginx、TLS、图片下载、登录高峰、持续预约写入、真实微信或短信服务，也不构成生产 SLA。

另一次过载探测设定 5,000 请求/秒、持续 15 秒：计划 75,000 次，客户端并行上限 256 导致 **56,026 次未发出**，实际完成 18,974 次，其中 18,920 次成功、54 次返回 503，完成速率约 1,245 次/秒，P95 为 476.49 ms。服务之后健康检查正常。**不能将它解释为支持 5,000 请求/秒，也不能用这次结果单独确定后端吞吐上限**；下一轮需要独立、更充足的压测端。见 [过载原始报告](capacity-overload-result.json)。

## 5 万访问规模的首期配置

5 万用户规模需要结合访问时间和操作频率评估。50,000 次访问若均匀分布在一天，平均约 0.58 次访问/秒；若集中在 10 分钟，约为 83.3 次访问/秒。一次访问通常包含多个 API 和图片请求，这两个数字都不能直接作为后端请求/秒或同时在线人数。以下为首期资源规划，最终以目标云环境测试为准。

| 资源 | 首期建议 | 扩容预留 |
| --- | --- | --- |
| 应用服务器 | 1 台标准型 CVM，4 核 8 GB，100 GB SSD；运行 Nginx 和 1 个 Java 实例 | 先观察 CPU、堆/GC 和接口延迟；可升为 8 核 16 GB，或补第二台应用服务器接 CLB |
| 数据库 | 独立云 MySQL，2 核 4 GB、100 GB SSD，优先双节点高可用，内网连接 | 慢查询和索引优化后仍有瓶颈，再升至 4 核 8 GB；同步复核所有实例连接池的总连接预算 |
| 公网带宽 | 建议先按 10 Mbps 规划；采用 5 Mbps 时必须通过对应带宽下的峰值测试 | 按实际动态响应流量调整至 20 Mbps 及以上，不按用户总数直接购买 100 Mbps |
| 图片和静态资源 | COS 按实际用量计费，100 GB 仅作为初始存储预算，公开资源经 CDN 分发 | 按访问流量和缓存命中率扩展；客户资料、预约、聊天等接口继续鉴权访问 |
| 监控与备份 | 应用、数据库、带宽告警；数据库自动备份及异地文件备份 | 上线前验证恢复，按增长调整备份保留周期和存储 |

首期采用一个应用节点，维护重启或主机故障会影响服务；需要主机故障期间继续服务时，再增加独立应用节点和负载均衡。当前代码未接入 Redis，先保留引入空间，待全局限流或缓存确有需求时接入。

5 Mbps 的理论传输上限约为 **625 kB/s**，10 Mbps 约为 **1.25 MB/s**，实际还要扣除协议开销。图片和页面资源通过 CDN 分发可减少应用服务器出口压力，但首次回源、动态 API 和上传仍需纳入测试。API 响应体大小和高峰访问频率共同决定带宽，不能单凭“5 万用户”判断 5 Mbps 是否够用。

现有阿里云 2 核 8 GB 可以继续用于联调或经实测的小流量试运行；迁移腾讯云时再按上述首期规格配置。具体性能取决于实例型号、磁盘、数据库及网络条件，云厂商更换本身不构成容量提升证明。

规划依据可查腾讯云 [CVM 实例规格](https://cloud.tencent.com/document/product/213/11518)、[MySQL 双节点架构](https://cloud.tencent.com/document/product/236/47906)、[CDN 原理](https://cloud.tencent.com/document/product/228/2939)及 [COS 产品说明](https://cloud.tencent.com/document/product/436/6222)。上述配置是本项目的起步建议，不是云厂商对本项目吞吐量的承诺，具体可选规格、库存和价格以所选地域控制台为准。

## 扩容条件与实施顺序

以下阈值作为首期告警和排查起点，需要结合实际业务高峰调整；除故障、持续拒绝请求等需立即处理的情况外，观察连续 5–10 分钟，排除异常流量、慢 SQL 和渠道故障后决定扩容：

1. 带宽持续超过已购上限的 80%，或图片加载明显变慢：检查 CDN 命中、压缩及响应体，再增加带宽。
2. 应用 CPU 持续超过约 70%，或读取 P95 超过 500 ms、预约写入 P95 超过 1 s：结合 GC、连接池等待和数据库指标定位瓶颈，再升级应用规格或增加节点。
3. 数据库持续出现资源饱和、连接池等待、慢查询或锁等待：先优化查询和事务，再升级数据库；主备中的备节点用于故障切换，不承担常规读取扩容。
4. 出现持续 429/503、超时或通知积压：分别检查访问频率、容量保护、外部渠道配额及发送速率，避免直接提高所有并发上限。扩容后重新验证容量和预约正确性。

当前模板支持同主机两个进程共享数据库和上传卷。跨主机扩容前必须先完成 COS/共享文件存储适配，使两个应用节点可访问相同上传文件，再配置 CLB、独立云数据库和各节点私网访问；这些云端适配与资源接入尚未完成。同机双实例不具备跨主机容灾能力。现有数据库协调预约、任务领取和幂等处理的基础可继续用于扩容。

## 云端上线验收要求

以 5 万客户、10 万笔历史预约作为首轮数据基线，并根据未来订单增长补充数据。先确认访问统计周期、真实用户行为、预约高峰和图片体积，再在目标 4 核 8 GB 云环境使用独立压测端，模拟首页、选店选项、查询时段、登录、预约、改期、客服和后台查询的真实比例。

第一轮可采用 50、100、200 请求/秒逐级探测，记录在已购带宽下的实际处理情况；这些是测试档位，尚未构成容量承诺。另按有停留时间的活跃会话模型测试登录和集中预约高峰，再根据测得的峰值及余量确定上线规模。5 万条数据、5 万次访问、请求/秒和同时在线人数分别统计。

建议验收条件需在目标云环境记录并确认：

1. 达到约定业务请求速率，连续运行至少 60 分钟，再做持续稳定性测试；统计全部计划请求、实际发送、客户端丢弃、429/503、超时和其他错误。达到保护上限不等于容量验收通过，不能从成功率中剔除拒绝请求。
2. 可先以读取 P95 ≤ 500 ms、预约写入 P95 ≤ 1 s、非业务预期错误率 < 0.1% 作为待确认指标。名额不足或版本冲突应单列为业务结果；微信、短信等第三方延迟单独记录。
3. 预约不超卖、不重复创建，手机号限制与版本控制跨实例一致；提醒、消息和导入记录可追溯。额外覆盖服务重启、数据库短暂故障和渠道超时后的恢复。
4. 同时记录 CPU、堆/GC、连接池等待、数据库慢查询/锁等待、磁盘、网络和队列深度，保留资源余量；据此确定实例数量和公网带宽。做备份恢复演练后再承接正式业务。

## 部署与复现

部署命令、密钥、TLS/代理来源、备份和扩容限制见 [生产部署说明](../deploy/README.md)。当前本地入口为 `http://127.0.0.1:8790/admin`。

测试命令（项目根目录）：

```powershell
mvn.cmd -B -ntp -f backend/pom.xml test
npm.cmd run build
npm.cmd run check:mini
```

隔离 MySQL 验证使用 `CapacityIntegrationTest` 的 `capacity.test-db-url`、`capacity.test-db-user`、`capacity.test-db-password` 参数，只接受测试代码允许的独立库地址。`CapacityLoadFixture` 仅使用固定的本机测试端口/数据库，要求首次种子为空库；不要修改为业务库。它产生的令牌元数据保存在不提交的 `backups` 目录。`tools/load-capacity.mjs` 和 `tools/verify-capacity-http.mjs` 同样校验隔离地址，不用于生产服务器压测。

本地 8790 已使用新构建的前后端运行，Flyway 从 V5 升级至 V6。更新前后完整核对预约、门店、调理师、用户、角色及点评配置，原有 12 笔预约、9 家门店、27 位调理师、4 个用户和 3 个角色全部保留，见 [业务资料核对](capacity-business-preservation-result.json)。浏览器只读检查确认总部角色权限、门店在“品牌与内容”编辑本店项目、三类通知及点评入口可正常进入，未保存业务资料，见 [本地页面检查](capacity-local-browser-result.json)。

此次源码、业务快照、旧运行包和升级前的数据库文件备份保存在 `backups/capacity-20261105-132502`。三个拆分仓库同步业务源码时保留了后端独立的 `./data` 路径和前端发布资源配置；合并工程仍是当前本地运行与容器部署入口。所有云端资源、付费渠道调用及生产数据库迁移均未执行；生产采用 MySQL 时仍需另行核验并迁移现有本地业务数据。
