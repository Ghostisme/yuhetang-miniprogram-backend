## 本次部署

使用本轮「店长通知与服务号菜单」整体服务器更新包及其 README。管理后台采用用户提供的 `175257` 前端产物，并配套包含服务号菜单接口及 V10 迁移的 Java。更新器先备份本项目独立库、上传目录、环境和前端，再同时设置店长模板 ID、环境字段映射及数据库 `serviceTemplateMapping`，重建 Java 使配置生效。

## 店长绑定

1. 升级后重新打开后台「消息中心 → 管理后台消息推送」，选择一家实际门店。
2. 点「检查店长服务号配置」，核对正式账号模板与五个字段；此按钮不发送真实消息。检查通过只是凭证、模板可用。
3. 在「用户管理」确认本店有有效的店长账号；总部账号本身不作为各门店接收人。
4. 选择本店账号，点「生成微信绑定链接」。本人在 15 分钟内用接收通知的微信打开，关注服务号，并点「本人确认绑定并接收通知」。
5. 后台点「刷新绑定状态」，应提示已确认绑定；开启「门店接收人微信提醒」，点「保存本店通知设置」。
6. 按店重复。每店当前一名微信接收人；换人后旧待发任务不会转给新接收人。历史阻断记录不自动补发，用新预约验证。

## 客户订阅弹窗

最终提交预约或改约时，点击动作直接调用微信 `requestSubscribeMessage`，申请两个模板的原生订阅授权。独立的“订阅预约及到店提醒”卡片已移除，无需另外操作。用户可以只允许其中一项；拒绝、取消或原生 API 失败不阻止预约。

系统弹窗中的“总是保持以上选择”由微信提供，记住偏好不会变成长期开关或无限次数，也不会因为读取设置就新增次数。用户已经记住选择时，微信可能不再重复展示同样的弹窗。下次提交预约或改约仍会请求本次授权；本地模拟身份和 H5 不能验证真实微信送达。

两个模板分别登记、分别使用。预约处理模板可用于确认、改期、取消或拒绝等处理结果，一次授权仅支持对应模板的一次发送；如需再次收到处理通知，客户要重新授权。到店提醒使用另一模板，需单独允许。

## 真机逐项验收

用一个客户微信和一个已绑定店长微信，备注写“通知验收”，只创建测试预约。先确认「消息中心」本店客户微信和店长微信开关已保存。

| 步骤 | 操作 | 应验证的结果 |
| --- | --- | --- |
| 1 | 客户真机预约并允许两个订阅模板 | 预约提交成功；后台出现待确认预约和铃铛消息；两个模板分别登记授权，不依赖已移除的订阅卡片 |
| 2 | 店长暂不处理该预约 | 店长服务号收到待接单提醒，含门店、项目、时间、客户名称和手机号；其他门店接收人没有该预约通知 |
| 3 | 管理后台确认预约 | 客户收到预约处理提醒；后台 PC 记录出现状态变化；当前待接单模板不再用于确认完成通知 |
| 4 | 等待进入到店前提醒时间范围 | 客户收到独立的预约提醒，次数只扣此模板；重复轮询不会再次发送同一条 |
| 5 | 新测试预约在可用授权下测试改期或取消；改约提交时再次请求授权 | 对应处理通知发送一次；旧预约状态/旧时间的待发提醒停止；取消操作不保证已有新授权 |
| 6 | 另一笔待确认预约超过营业时间内 15 分钟 | 店长收到待确认超时提醒；已处理预约不再收到旧待接单提醒 |
| 7 | 后台开启/测试桌面提醒，切到其他标签页，产生新预约/咨询 | 电脑保持唤醒、浏览器和后台开启时出现桌面提醒；两个标签页不重复弹同一条；历史未读不在登录时集中弹出 |
| 8 | 客户先后测试“微信客服”和“在线咨询” | 两种会话均在客户沟通找到；后台 Enter 发送、Shift+Enter 换行；手机实际收到回复；输入法选词不误发送 |
| 9 | 客户拒绝订阅，再提交预约 | 预约仍成功，未授权模板不显示为已发送，后台有明确未发送原因 |

到店提醒任务每分钟扫描。测试时间必须符合本店最短提前分钟、营业时间、可预约日期和名额规则；可使用一笔较近的测试预约，在到店前提醒范围等待至少一个扫描周期，无需改全店生产规则。待确认超时按营业分钟累计，非营业时间不计时。

发送记录 `ACCEPTED` 表示微信受理，手机实际收到才算链路验收通过；`BLOCKED` 说明授权、绑定、模板或配置未满足；`UNKNOWN` 结果待核实，先查手机与平台再决定后续，系统不盲目重发。记录不会因为新版部署就抹掉以前失败的历史。

## 本地验证范围

- Java：140 项测试通过，覆盖模板字段、真实 HTTP 请求格式（固定 Content-Length）、客服回调、授权次数、单次消费、任务去重、过期取消、预约提醒调度、门店隔离和本人绑定。
- 小程序：类型检查及 13 项测试通过；Taro 微信与 H5 生产构建通过。原生设置偏好不会凭空产生授权次数；原生 Promise 失败会正常结束预约订阅步骤。
- 后台：TypeScript/Vite 构建通过；10 项隔离浏览器检查通过，包含两种消息视图、绑定刷新、1366/2560 布局、只读权限、两个标签页通知去重和后台轮询。浏览器测试使用构建产物与模拟 API，不发送真人消息。
- 配置工具：5 项测试通过，验证仅修改指定字段、保留原配置和拒绝无效映射。

上述验证不等同于已在腾讯云部署，也不证明真实微信送达；真实手机验收按上表记录。服务号 AppSecret、OAuth 本人确认及发送权限仍以服务器实际配置和微信接口结果为准。
