## 三、验证真实客服

用客户微信发送一条新文字，然后读取这次 Java 日志。当前小程序未开通云开发，无需检查或开通云开发配置：

```bash
docker logs --since 10m --tail 200 yuhetang-java-api 2>&1 |
  grep -E 'WeChat callback|WeChat customer send'
```

这里 `grep` 返回状态 1 仅表示选定时间内没有匹配日志，不代表 Java 服务启动失败。先确认运行中的镜像和 JAR 校验值均为新版本，再用一条新客户消息触发回调。

- `type=event event=user_enter_tempsession outcome=ENTRY`：只进入了客服窗口。
- `type=text event=none outcome=STORED`：客户文字已入库，应在后台出现。
- `outcome=DUPLICATE`：同一消息的重复推送已去重。
- `outcome=REJECTED` / `ERROR`：用同一行 HTTP 状态或异常类别定位。
- 只有进入事件、没有文字回调：继续检查微信文字的实际投递路径。

后台出现这条新文字后，再回复一次。新的失败气泡将显示响应超时、TLS 失败、HTTP 状态或响应解析失败等具体原因；日志里的 `category` 与该原因对应。未知结果不会自动重发，旧的两条 `UNKNOWN` 历史也不会自动改成成功。以客户手机实际收到这次新回复作为发送验收。

门店资料另用 `yuhetang-official-stores-20261107.zip` 导入，Java 更新不自动填充门店。操作见[官网门店初始化](官网门店初始化.md)。

## 手动回退到更新前的 Java

启动失败时脚本已自动尝试恢复旧版本。若新版本启动健康，但后续业务验收需要回退，使用脚本输出的真实备份名。先查看，不要删除任何容器：

```bash
sudo docker ps -a --format '{{.Names}}  {{.Image}}  {{.Status}}'
```

确认备份仍在并处于停止状态后，在 root 终端逐行执行。将第一行示例名称替换成脚本输出的真实备份名；如不确定名称，先停在查看步骤。

```bash
YHT_PREVIOUS='yuhetang-java-api-before-215000-替换成实际时间和进程号'
YHT_FAILED="yuhetang-java-api-manual-rollback-$(date +%Y%m%d-%H%M%S)"
docker container inspect "$YHT_PREVIOUS" >/dev/null && docker stop --time 50 yuhetang-java-api && docker rename yuhetang-java-api "$YHT_FAILED" && docker rename "$YHT_PREVIOUS" yuhetang-java-api && docker start yuhetang-java-api
```

此版本与原版数据库结构一致，回退只切换 Java 容器，不恢复或清空数据库。重新检查健康接口确认旧服务恢复；客服历史消息保持原样。
