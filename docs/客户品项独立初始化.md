## 门店独立数据

同名项目也通过本店专属品项接口分别建档，生成各自的 `svc-…` ID。价格、时长、介绍、上下架和排序只对本店生效。资料中的 20 个品项定义是整理来源的索引，不是写入总部的共用品项。

初始化将这 9 家门店切换为 `catalogMode=INDEPENDENT`。它们的客户展示、预约选择、前台代约和调理师可选项目均读取本店记录，总部新增或停用品牌模板不再改变这些门店的目录。尚未切换的门店继续使用原有继承规则。

已有且能唯一匹配名称／英文名的本店专属项目保留原 ID；遇到歧义就停止，不猜测归属。不会删除其他已有的本店专属项目。原来的总部模板和历史预约保留。

本次只初始化品项、切换目录管理方式、归档 9 张压缩价目图片。不更改门店地址、相册、营业时间、预约规则、客户、订单、账号或调理师资料。新项目与调理师技能的关联请在“调理师管理”中按实际资质勾选，不自动分配。

当前系统的品项表单没有独立的结算价格字段，因此参考价格写入“简短说明”和“详细介绍”；完整人民币分档价格、来源和待确认标识保存在 `services.json` 及导入报告中。每项计费不推算固定分钟数；未明确的价格不补成统一价格。对照表见包内 `initial-data/client-services-20261108/品项资料核对表.md`。

## 服务器更新和导入

本次需要先更新 Java，增加独立门店目录支持。管理后台静态文件和 Taro 小程序不需要为这批数据重新构建发布。继续使用已经配置好的 `mp-admin.hetuonian.cn` 和现有网关、MySQL。

发布时会将下列 `@RELEASE_ID@`、`@ACTIVATION_ID@` 替换为实际编号。把下列 6 个文件上传到 `/home/ubuntu/`：

- `yuhetang-java-docker-@RELEASE_ID@.tar.gz` 及其 `.sha256`；
- `yuhetang-activate-@ACTIVATION_ID@.sh` 及其 `.sha256`；
- `yuhetang-client-services-@RELEASE_ID@.zip` 及其 `.sha256`。

先在 ubuntu 终端校验并激活 Java。激活器在停止旧 Java 前先校验、构建，保留旧容器，并在启动健康检查失败时尝试恢复。它不操作 MySQL 容器或 OpenResty：

```bash
cd /home/ubuntu
sha256sum --check yuhetang-java-docker-@RELEASE_ID@.tar.gz.sha256
sha256sum --check yuhetang-activate-@ACTIVATION_ID@.sh.sha256
sudo bash ./yuhetang-activate-@ACTIVATION_ID@.sh
```

应显示当前新镜像 `yuhetang-java-api:@RELEASE_ID@`、`Health=healthy` 和 `database=connected`。接着校验、解压资料包：

```bash
cd /home/ubuntu
sha256sum --check yuhetang-client-services-@RELEASE_ID@.zip.sha256
sudo install -d -o root -g root -m 0700 /root/yuhetang-upload
sudo python3 -m zipfile -e yuhetang-client-services-@RELEASE_ID@.zip /root/yuhetang-upload
sudo -i
```

进入 root 后再逐行执行。下面的预览只读接口，不写入门店、品项或图片；要求目标服务器已经存在这 9 家门店：

```bash
cd /root/yuhetang-upload/yuhetang-client-services-@RELEASE_ID@
sha256sum --check SHA256SUMS
python3 tools/initialize-client-services.py --validate-only
python3 tools/initialize-client-services.py --username admin
```

最后一条会提示输入管理后台总部账号密码，输入时不回显；若总部账号不是 `admin`，将参数改成实际账号。脚本调用本机 `http://127.0.0.1:8790` 的管理 API，不需要数据库 root 密码。

确认预览列出的各店项目和待确认项后，执行正式初始化：

```bash
python3 tools/initialize-client-services.py --username admin --apply
```

成功末尾显示 `Verified: 9 stores, 135 independent items (126 active, 9 pending/off)`。如果本来已经有同名的本店项目，会复用它们的 ID，因此新建数量可能少于 135。9 张价目图可在“图片素材”按 `client-menu-` 查找；品项封面仍使用已有的项目图片。

在后台“品牌与内容 → 养护项目”选择具体门店查看，而“全部门店”仍是总部品牌模板。客户小程序重新进入门店页面可读取本店项目；本地开发工具若仍有旧缓存，重新编译后再看。可核对梅花路店没有 SPA／足疗／C／D 套餐，且 A 套餐是经络疏通＋扶阳悬灸；上海中心店与余姚路店的推拿价格也不同。

## 重复执行、备份和中断

每次正式导入前，将原门店资料、品项、预约规则和总部内容保存在包目录的 `backups/client-services/<时间编号>/before.json`，执行进度及生成的实际品项 ID 保存在同目录 `report.json`。这个目录不放到网站目录。

同一批资料原样再次执行时，匹配并复用各店原 ID 和同校验值的价目图，不重复新建。初始化工具会按资料重新写回匹配到的项目字段；导入后已手工调整过品项时，应先预览，避免将有意修改覆盖回来源资料。

单店项目批量保存使用数据库事务和版本号；跨门店导入逐店进行，不是一个跨店事务。新增条目先下架，准备好后再按资料批量开启；遇到并发编辑、接口失败或来源歧义立即停止并保留报告。不会自动删除已经创建的条目，也不会宣称跨店全部回滚。处理错误前保留报告；如果确需恢复，按 `before.json` 恢复本项目资料，并将本次新建条目下架。需要恢复库文件时使用本项目独立数据库的已验证备份，不恢复整个 MySQL 实例。

完成导入后若回退到不支持独立目录的旧 Java，旧程序仍会合并总部模板。应同时按导入前备份恢复目录状态，或保留支持独立目录的后端版本。

```powershell
python -X utf8 -m unittest discover -s tools -p test_initialize_client_services.py -v

```

原始客户 PDF 和 JPG 保持不变；压缩图片的原文件名、原始校验值、当前校验值和人工核对规则均保存在资料清单中。服务器导入只需要 Python 3 标准库，Pillow 仅供本地重新整理图片使用。
